## Findings

### 1. MEDIUM: Prompt piped to stdin but codex may expect different input format

**Location:** `.github/workflows/anvil-review.yml:104`

**Description:** The command pipes the prompt to `codex exec` via stdin:
```bash
printf '%s' "$PROMPT" | codex exec --dangerously-bypass-approvals-and-sandbox -
```

The hammer workflow uses:
```bash
claude --print --output-format json --dangerously-skip-permissions --max-turns ${MAX_TURNS} "$PROMPT"
```

Note that `claude` receives the prompt as a command-line argument while `codex` receives it via stdin (indicated by the trailing `-`). This is likely intentional based on differing CLI interfaces, but should be verified that the prompt format generated by `build_prompt.py` is compatible with both tools.

**Impact:** If the prompt format is incompatible with Codex's expected input, the review may fail or produce incorrect results.

### 2. LOW: MAX_TURNS defined but not used

**Location:** `.github/workflows/anvil-review.yml:22`

**Description:** The environment variable `MAX_TURNS: 30` is defined but never referenced in the anvil workflow:
```yaml
env:
  SPRITE_NAME: anvil
  REVIEWER_NAME: anvil
  SKIP_TOKEN: skip-anvil
  MAX_TURNS: 30  # Never used
```

In contrast, `hammer-review.yml` uses `--max-turns ${MAX_TURNS}` in the claude command. The codex command does not include a similar flag.

**Impact:** Low - the variable is unused but harmless. It may indicate a copy-paste from hammer-review.yml without full adaptation.

### 3. LOW: REVIEWER_NAME defined but not used

**Location:** `.github/workflows/anvil-review.yml:20`

**Description:** `REVIEWER_NAME: anvil` is defined but never referenced in the workflow.

**Impact:** Low - unused variable, likely intended for future use or documentation purposes.

### 4. INFO: Same prompt source for different AI backends

**Location:** `.github/workflows/anvil-review.yml:82`

**Description:** Both workflows fetch the same prompt from `agent-harness/main/scripts/hammer/build_prompt.py`:
```bash
PROMPT_B64="$(curl -fsSL -H "$AUTH_HEADER" https://raw.githubusercontent.com/r-mccarty/agent-harness/main/scripts/hammer/build_prompt.py | python | tr -d '\n')"
```

The prompt is labeled "hammer" but is being used for "anvil". This may work if the prompt is generic, but could cause confusion in naming/maintenance.

**Impact:** None functionally, but creates naming inconsistency between the prompt source path (hammer) and the workflow (anvil).

### 5. INFO: No output capture mechanism

**Location:** `.github/workflows/anvil-review.yml:104`

**Description:** The codex output is not captured or saved. The hammer workflow uses `--output-format json` which implies structured output handling. The anvil workflow simply runs codex and any output goes to stdout/stderr of the sprite exec command.

**Impact:** Review results may not be easily accessible or parseable. This may be intentional if the codex tool handles its own output (e.g., creating files directly).

### 6. INFO: Duplicate workflow triggers on same branches

**Location:** `.github/workflows/anvil-review.yml:3-8`

**Description:** Both `anvil-review.yml` and `hammer-review.yml` trigger on the same branches (main, dev, feature/**). This means every push will trigger two separate AI review workflows unless explicitly skipped.

**Impact:** Increased CI runtime and resource usage. May be intentional for comparison testing between Claude and Codex.

## Recommended Actions

1. **Verify codex input format** - Confirm that the prompt generated by `build_prompt.py` works correctly when piped to `codex exec` via stdin.

2. **Clean up unused variables** - Consider removing `MAX_TURNS`, `REVIEWER_NAME`, and `SKIP_TOKEN` if they are not used, or document their intended purpose.

3. **Consider prompt source naming** - If the prompt will be shared between hammer and anvil, consider renaming the path to something generic like `scripts/review/build_prompt.py`.

4. **Monitor parallel execution** - Both workflows will run on every push to dev/main/feature branches. Ensure this is the intended behavior and resource usage is acceptable.

5. **Add output handling** - Consider whether codex review output needs to be captured or if the tool handles its own file creation (similar to how claude creates RFD files).
